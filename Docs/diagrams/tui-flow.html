Project Init / Program flow / 31 Aug 2026

From a brief to a validated project.

The terminal workbench is the hub. It saves project knowledge, starts background work, and brings you back whenever the workflow needs an answer, a decision, or permission to repair.

01 / Enter the workbench

Interactive terminal · ordinary new / open path

SQLite owns project state

The TUI holds a disposable snapshot. Answers, findings, requirements, decisions, and workflow status persist through service operations. Returning from a worker reloads the project; reopening a project does not restart its analysis.

Provider work is provisional

The selected Codex, OpenCode, or local provider works behind the same workflow boundary. Activity is progress, not acceptance. Initial structured output must validate; documentation is staged before adoption.

02 / Follow the workflow

The runner replans from saved state after each accepted step

Questions and decisions are separate gates

A question blocks only when its priority meets the clarification threshold. Approval depends on the chosen policy. /auto-answer can research questions; it does not grant decision authority or authorize repairs.

Completion is checked, not assumed

Validation checks stored relationships and document outputs. Mechanically safe fixes may be local; remaining repair findings pause the run. Provider repair needs authorization, obeys the repair limit, and preserves document overrides.

03 / Commands & controls

What changes state, and what starts work

InputEffect
Answer text + EnterAnswers the selected open question; saves the result and advances the question selection. Use /answer <question-id> <text> to target one explicitly.
/ask [prompt]Opens the structured question form. Enter creates the question; Esc discards the draft.
/threshold <1-125>Changes which question priorities block the workflow.
/resumeStarts or resumes work until the next boundary. The first run opens a policy selector with no default.
/auto-answerStarts the same runner with automatic clarification and a coordinator / workers / judge progress board. The first run still requires a policy choice.
/approve / /rejectRequires a decision ID and reason. Saves the decision, then waits for /resume.
/repairAuthorizes one repair attempt. It does not execute the repair until /resume.
Tab · ← → · ↑ ↓Tab moves focus. Outside the composer, Left/Right changes section; Up/Down selects questions or scrolls read-only content. Page Up/Down and Home/End scroll read-only panels.
Esc / qWhile a worker runs, Esc requests cancellation and waits for acknowledgement. In the composer, Esc returns to content. In navigation/content, Esc or q closes the workbench. Cancellation keeps previously accepted work resumable.
Source map, scope, and diagram assumptions

Based on the current working-tree source on 31 August 2026, including uncommitted code. These two 1280 × 720 flowcharts describe the interactive workbench at a balanced level of detail. The overview combines analysis, validation, and atomic creation into one stage; the workflow combines package freshness checks and generation into one stage. Provider transport internals, the legacy inspection view, and headless CLI branches are outside the diagrams.

  • src/main.rs — create_project, report_created_project, and open_project route creation and reopening into the terminal workbench. Redirected open emits JSON. Explicit new --offline uses deterministic analysis and skips the live provider creation view.
  • src/tui/mod.rs — run_workspace_with_initial_mode drains worker events, renders, handles keys, and reloads results; apply_interactive_workspace_command distinguishes saved edits from background execution.
  • src/tui/workspace.rs — submit_composer, focus-specific key handlers, and workflow_guidance_lines define commands, policy selection, next-action prompts, and progress overlays.
  • src/workflow/runner.rs — run_until_pause_with_auto_answer_progress runs steps until a boundary, completion, cancellation, or error, and coordinates automatic question research.
  • src/workflow/mod.rs — workflow_status prioritizes blocking questions, pending approval, a missing/stale package, open repair findings, a prior passing validation, then validation. The visual groups these checks for readability; it does not imply regeneration or repeated validation on every resume.
