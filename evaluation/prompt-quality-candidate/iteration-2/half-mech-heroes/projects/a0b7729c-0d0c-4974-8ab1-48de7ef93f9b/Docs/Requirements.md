## Acceptance Criteria
AC-001: Inspect the startup title and build metadata; pass if both display exactly "Half-Mech Heroes" and fail otherwise; AC-001 supports REQ-001 because the inspected Half-Mech Heroes title is the REQ-001 project title.
AC-002: Start a clean local session with two human input stations and no network connection; pass if both players can contribute simultaneously and fail otherwise; AC-002 supports REQ-002 because the two local human stations objectively exercise the local two-player couch arcade game.
AC-003: Inspect one active session; pass if both players' accepted actions mutate one and only one rescue-mech entity and fail if either controls a separate avatar; AC-003 supports REQ-003 because one rescue-mech entity is the same malfunctioning rescue mech operated by both players.
AC-004: Using the default controller scheme, actuate only the left stick or directional control and the designated left-side jump input; pass if they move and jump the mech while no right-side input is required and fail otherwise; AC-004 supports REQ-004 because the observed movement and jumping use the gamepad left side.
AC-005: Using the default controller scheme, actuate only the right stick and designated right-side shield input; pass if they aim the magnetic arm and shield while no left-side input is required and fail otherwise; AC-005 supports REQ-005 because the observed magnetic arm and shield aiming use the gamepad right side.
AC-006: Apply one confirmed damage event to the mech in each current role assignment; pass if exactly one automatic role swap occurs after each event and fail if zero, multiple, or manual-only swaps occur; AC-006 supports REQ-006 because each mech damage event objectively triggers the automatic role swap.
AC-007: Complete one attempt while recording level instances; pass if play traverses exactly one continuously scrolling disaster-zone instance and fail if a second zone or non-scrolling level is loaded; AC-007 supports REQ-007 because the instance count and camera motion inspect the single scrolling disaster zone.
AC-008: Spawn the prototype civilian type in a falling state and perform the catch action; pass if the civilian transitions to caught without ground impact and fail otherwise; AC-008 supports REQ-008 because the falling-civilian state transition objectively demonstrates catching falling civilians.
AC-009: Place magnetic wreckage across the traversable route and perform a throw; pass if the wreckage becomes displaced beyond the route clearance boundary and fail otherwise; AC-009 supports REQ-009 because the clearance observation demonstrates throwing wreckage out of the way.
AC-010: Execute the stakeholder-approved multiplier triggers before the timer reaches zero; pass if the visible teamwork multiplier increases according to the approved rule and fail otherwise; AC-010 supports REQ-010 because the visible pre-timeout increase inspects the teamwork multiplier, but execution is blocked by OQ-008.
AC-011: Measure the active-attempt clock from start signal to timeout; pass if elapsed time is 180.0 seconds with tolerance no greater than one simulation tick and fail otherwise; AC-011 supports REQ-011 because 180 seconds is exactly the three-minute rescue attempt.
AC-012: From the end-state screen, issue restart on reference hardware and measure until both players regain control; pass if the same block is playable within 5.0 seconds and fail otherwise; AC-012 supports REQ-012 because the measurable 5.0-second restart threshold operationalizes quick restarts under ASM-002.
AC-013: Run the standard-wreckage physics test scene; pass if one default throw moves the wreckage centre at least two mech-heights horizontally before rest and one damage recoil rotates the mech at least 15 degrees before recovering within 0.8 seconds, and fail otherwise; AC-013 supports REQ-013 because the exact distance, angle, and recovery inspections objectively test exaggerated physics under ASM-008.
AC-014: Render the mech, civilian, and each approved hazard as solid black masks against solid white at the television test setup; pass if five of five evaluators correctly identify every class on first display and fail otherwise; AC-014 supports REQ-014 because first-display mask identification tests the chunky silhouettes under ASM-003.
AC-015: Trigger every tagged mechanical-failure event for five independent dyads; pass if each event produces a distinct audiovisual beat without obscuring the active role or hazard and at least four dyads mark at least one beat as funny, and fail otherwise; AC-015 supports REQ-015 because complete event inspection plus the four-of-five humour observation objectively tests funny mechanical failures under ASM-005.
AC-016: At the television test setup, show gameplay captures containing each HUD state, role state, civilian state, hazard, and failure; pass if five of five evaluators correctly identify every prompted state within two seconds and fail otherwise; AC-016 supports REQ-016 because timed state identification objectively tests television readability under ASM-003.
AC-017: Run the complete action checklist once with two connected controllers and once with one shared keyboard; pass if every required action is accepted in both configurations and fail otherwise; AC-017 supports REQ-017 because the two-controller and shared-keyboard runs inspect both required input configurations.
AC-018: Inspect the prototype content manifest and traverse one full attempt; pass if exactly one city-block level is declared and loaded and fail otherwise; AC-018 supports REQ-018 because the declared and loaded level count objectively tests one city block.
AC-019: Inspect the civilian archetype registry and spawn log; pass if exactly one civilian type is declared and spawned and fail otherwise; AC-019 supports REQ-019 because the registry and spawn counts objectively test one civilian type.
AC-020: Inspect the hazard registry and spawn log; pass if exactly three distinct stakeholder-approved hazard types are declared and all three spawn during the test attempt and fail otherwise; AC-020 supports REQ-020 because the registry and spawn counts objectively test three hazards, but their identities are blocked by OQ-006.
AC-021: Conduct the scripted dyad playtest with five dyads; pass if at least four dyads improve their successful coordinated-action count between attempts one and three and at least four independently report one observed mechanical-failure moment as funny, and fail otherwise; AC-021 supports REQ-021 because improvement tests coordination mastery and the independent report tests coordination comedy under ASM-005.
AC-022: Inspect the approved scope record before implementing remapping; pass if OQ-001 remains open or is replaced by a stakeholder-authored answer and fail if a delivery choice is inferred from external guidance; AC-022 supports REQ-022 because the inspection preserves input remapping as an open question.
AC-023: Inspect the approved scope record before implementing solo play; pass if OQ-002 remains open or is replaced by a stakeholder-authored answer and fail if solo inclusion or exclusion is inferred; AC-023 supports REQ-023 because the inspection preserves solo play as an open question.
AC-024: Inspect the approved scope record before implementing difficulty scaling; pass if OQ-003 remains open or is replaced by a stakeholder-authored answer and fail if a scaling model is inferred from guidance; AC-024 supports REQ-024 because the inspection preserves difficulty scaling as an open question.
AC-025: Inspect the approved audience record before assigning an exact target age; pass if OQ-004 remains open or is replaced by a stakeholder-authored answer and fail if a rating category is treated as the target age; AC-025 supports REQ-025 because the inspection preserves the exact target age as an open question.

## Constraints
CON-001: Each active attempt is constrained to "short three-minute rescue attempts"; CON-001 supports REQ-011 because the three-minute attempt duration is the same session subject.
CON-002: Scope is constrained to "The first prototype" rather than a production release; CON-002 supports REQ-017 because the first-prototype boundary governs the two-controller and shared-keyboard support.
CON-003: Prototype level content is constrained to "one city block"; CON-003 supports REQ-018 because the city-block count is identical.
CON-004: Prototype civilian content is constrained to "one civilian type"; CON-004 supports REQ-019 because the civilian-type count is identical.
CON-005: Prototype danger content is constrained to "three hazards"; CON-005 supports REQ-020 because the hazard count is identical while OQ-006 preserves the unspecified hazard identities.
